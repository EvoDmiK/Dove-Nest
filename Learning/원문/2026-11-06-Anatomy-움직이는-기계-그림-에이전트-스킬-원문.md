# Anatomy: 상자와 화살표 대신 움직이는 기계 그림으로 기술 개념을 설명하는 에이전트 스킬

## 핵심 요약

* [Anatomy](https://github.com/wheresryan22/anatomy)는 기술 개념을 상자와 화살표 대신, 그 개념대로 움직이는 가상의 기계 그림으로 만드는 에이전트 스킬입니다. 예를 들어 LRU(Least Recently Used) 캐시는 4칸짜리 책장이 되고, 블룸 필터는 릴 3개짜리 슬롯머신이 됩니다.
* Claude Code를 기준으로 작성됐고 Antigravity, OpenCode, Codex, MiniMax Code에서도 동작하며, 결과물은 Node 빌드 스크립트와 HTML 페이지, 단독 SVG, React 컴포넌트 같은 소스 코드로 남습니다.
* 기하 감사(audit), 선 끝 검사, 헤드리스(headless) Chrome 스크린샷처럼 에이전트가 자기 그림을 스스로 검증하는 도구가 함께 들어 있습니다.
* 큰 그림일수록 작업 시간이 길어집니다. 저자가 공개한 에이전트 작업 시간은 시계 무브먼트 1시간 54분, Raptor 엔진 10시간 33분이며, 3D 모드는 아직 베타입니다.

## Anatomy 소개

블로그나 기술 문서에서 시스템의 동작을 설명할 때 가장 흔히 쓰는 그림은 상자와 화살표입니다. 상자는 구성 요소가 있다는 사실을 알려주지만 그 구성 요소가 무엇을 하는지는 보여주지 못하고, 화살표가 뜻하는 움직임은 독자가 머릿속으로 그려야 합니다. 이번에 소개하는 Anatomy는 이 문제를 반대 방향에서 접근하는 에이전트 스킬(Agent Skill)입니다. 설명할 개념을 그대로 수행하는 기계를 에이전트가 직접 발명하고, 그 기계를 조작할 수 있는 아이소메트릭(isometric) 그림으로 만들게 합니다.

Anatomy가 가장 먼저 지키는 규칙은 *"The object is the explanation."* 으로, 그림 속 물체 자체가 설명이어야 한다는 원칙입니다. 바뀐 것이 없을 때 작업을 건너뛰는 캐시 키는 모든 핀이 맞을 때만 돌아가는 핀 텀블러 자물쇠가 됩니다. GPU 컨텍스트 하나가 여러 캔버스를 처리하는 구조는 프린트 헤드 하나가 16개 웰을 오가는 갠트리 플로터가 됩니다. 그림은 수십에서 수백 개의 작은 입체 부품으로 조립되고, 제목과 조작 안내, 실시간 수치(readout)가 붙은 카드 안에서 포인터와 키보드에 반응합니다. 그림에 표시되는 모든 수치는 부품을 움직이는 것과 같은 작은 모델에서 나오므로, 움직임과 숫자가 서로 어긋나지 않습니다.

![Anatomy 예제 중 화염을 뿜는 Raptor 2 엔진 시험대 그림|900x940](https://discuss.pytorch.kr/uploads/default/original/3X/9/7/97075c1fb8dd15925b026fdb91512d6b9a956709.webp)

Anatomy는 Ryan([@wheresryan22](https://github.com/wheresryan22))이 공개한 스킬로, 2026년 10월 8일 공개 저장소로 전환되기 전까지 `isometric-objects`라는 이름으로 개발됐습니다. [Claude Code](https://code.claude.com/docs/en/overview)를 기준으로 작성됐지만 [Agent Skills](https://agentskills.io) (:pytorch::kr: https://discuss.pytorch.kr/t/anthropic-agent-skills-aaif-skill-md/12278) 형식을 따르므로 [Antigravity](https://antigravity.google), [OpenCode](https://opencode.ai/docs/skills/), [Codex](https://developers.openai.com/codex/skills), [MiniMax Code](https://github.com/MiniMax-AI/minimax-code)에서도 불러올 수 있습니다. 저장소에는 에이전트가 읽는 [`SKILL.md`](https://github.com/wheresryan22/anatomy/blob/main/SKILL.md), 아이소메트릭 카메라와 부품 라이브러리를 담은 [`kit/`](https://github.com/wheresryan22/anatomy/tree/main/kit), 긴 참고 문서인 [`references/`](https://github.com/wheresryan22/anatomy/tree/main/references), 헤드리스 Chrome 검사 스크립트, 그리고 완성된 예제 8개가 들어 있습니다. 위 그림은 그중 Raptor 2 엔진 예제로, 엔진과 시험대는 SVG로 그리고 배기 화염만 같은 아이소메트릭 카메라를 쓰는 [WebGL](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API) 셰이더로 그립니다.

## Anatomy와 다른 다이어그램 스킬 비교

PyTorchKR에서 소개한 다이어그램 계열 에이전트 스킬은 대부분 상자와 연결선으로 된 도식을 더 잘 그리는 데 초점을 둡니다. Anatomy는 도식을 그리지 않는다는 점에서 출발점이 다릅니다. 아래 표는 각 저장소의 현재 README를 기준으로, 각 스킬이 무엇을 그리고 결과를 어떤 형태로 남기며 무엇에 공을 들였는지를 정리한 것입니다:

| 항목 | **Anatomy** | [Diagram Design](https://discuss.pytorch.kr/t/diagram-design-claude-code/10703) | [drawio-skill](https://discuss.pytorch.kr/t/drawio-skill-draw-io/10750) | [Archify](https://discuss.pytorch.kr/t/archify/11536) |
|---|---|---|---|---|
| 그리는 것 | 개념대로 움직이는 가상의 기계 | 아키텍처, 플로우차트 등 45가지 도식 | ERD, 시퀀스, C4, 아키텍처 등 11가지 프리셋 도식 | 아키텍처, 워크플로, 시퀀스 등 10가지 도식과 설명 페이지 |
| 결과물 | Node 빌드 스크립트와 HTML 페이지, 단독 SVG, React 컴포넌트 | 자체 완결형 HTML과 SVG | 편집 가능한 `.drawio`와 PNG/SVG/PDF, 인터랙티브 HTML 뷰어 | 단독 HTML 파일과 PNG/WebP/JPG 이미지, PDF |
| 움직임 | `interactive`를 요청하면 포인터와 키보드에 반응하고 실시간 수치 표시 | 정적 그림 | 애니메이션 데이터 흐름 SVG 내보내기 | 경로 추적 같은 탐색 기능과 모션 형식 내보내기 |
| 공을 들인 부분 | 기하 감사와 선 끝 검사로 그림 자체를 검증 | 사용자 사이트의 색과 글꼴을 읽어 브랜드에 맞춤 | 코드, Terraform, OpenAPI 등에서 도식을 만들고 변경을 추적 | 타입이 정의된 JSON 중간 표현과 레이아웃 검증기 |

선택 기준은 그림이 무엇을 전달해야 하는가입니다. 여러 서비스의 연결 관계처럼 구조 자체를 보여줘야 한다면 도식형 스킬이 맞고, Anatomy 저자도 만들 메커니즘이 없는 아이디어는 결과가 약해진다고 한계 항목에 적어 두었습니다. 반대로 토큰 버킷 레이트 리미터나 언어 모델의 온도(temperature)처럼 시간에 따라 상태가 바뀌는 동작을 설명하는 것이 Anatomy가 노리는 영역입니다.

## Anatomy를 사용하면 좋을 사용자

기술 블로그, 문서 사이트, 강의 자료에 알고리즘이나 시스템의 동작을 독자가 직접 조작해 볼 수 있는 그림으로 넣고 싶은 작성자에게 Anatomy가 맞습니다. 결과물이 소스 코드로 남고 부품과 수치, 움직임이 같은 모델을 읽으므로, 숫자 하나를 고쳐 그림 전체를 갱신하는 식으로 직접 유지보수할 수 있습니다. 다만 큰 그림은 에이전트 작업이 열 시간을 넘기고, 저자에 따르면 48시간 넘게 걸리며 토큰을 모두 소진하는 렌더링도 있습니다([#41](https://github.com/wheresryan22/anatomy/issues/41)). **구조도 한 장을 빨리 그려야 하거나 데이터 차트가 필요한 경우에는 Anatomy가 적절한 선택지가 아닙니다.**

## Anatomy의 작업 흐름

Anatomy의 `SKILL.md`는 에이전트에게 10단계 작업 순서를 지시합니다. 핵심은 앞의 네 단계로, 기하 도형을 하나도 그리기 전에 실제 수치를 모으고, 개념에 맞는 기계를 정하고, 부품 목록부터 작성하게 합니다:

1. 크기 정하기: Figure, Hero, Epic 중 하나로 규모를 정합니다.
2. 사실 먼저: 크기, 개수, 임계값 같은 실제 수치를 작은 순수 모듈로 작성하고, 실시간 수치와 움직임과 캡션이 모두 이 모델을 읽게 합니다.
3. 물체 발명: 개념과 일대일로 대응하는 기계, 도구, 계기, 가구를 고르고, 무엇이 움직이고 그 움직임이 무엇을 뜻하는지 한 문장으로 적습니다.
4. 부품 목록: 받침, 구조, 메커니즘, 조작부, 강조 대상으로 나눠 최소 40개 부품을 적습니다.
5. 공간 계획: 월드 단위, 평면 배치, 카메라를 정합니다.
6. 기하 계산: 정적인 경로는 모두 미리 계산하고, 움직이는 부품은 정지 위치에서 만든 뒤 이동시킵니다.
7. 뒤에서 앞으로 칠하기: 화가 알고리즘(painter's algorithm) 순서로 그리고, 다른 부품을 감싸는 부품은 앞뒤 두 조각으로 나눕니다.
8. 카드 구성: 그림 번호, 제목, 조작 안내, 실시간 수치를 카드 네 모서리에 둡니다.
9. 움직임 부여: 시간 기반의 차분한 움직임과 아무도 만지지 않을 때 도는 기본 투어를 넣습니다. 화면 밖으로 나가면 멈추고, 실시간 수치는 바뀔 때마다 스크린 리더에 전달되며, 동작 줄이기(reduced motion) 설정에서는 움직임만 멈추고 입력에는 계속 반응합니다.
10. 비평가처럼 검증: 스크린샷, 감사, 4배 확대 점검을 문제가 없을 때까지 반복합니다.

첫 단계의 규모 구분은 작업 시간과 진행 방식을 함께 정합니다. 아래 표는 현재 `SKILL.md` 기준입니다:

| 규모 | 내용 | 진행 방식 |
|---|---|---|
| Figure | 메커니즘 하나, 부품 40~80개, WebGL 레이어 최대 1개 | 묻지 않고 바로 만들며 예상 시간은 알리지 않음 |
| Hero | 부품 80~150개, WebGL 레이어 여러 개 또는 3D 대상 하나 | 약 2~4시간이 걸린다고 알린 뒤 진행 |
| Epic | 차량, 건물, 플랜트 전체 또는 3D 대상 여러 개 | 6시간 이상이므로 시작하지 않고 Hero 버전을 먼저 제안 |

홈페이지의 같은 표에는 Figure가 30~90분으로 적혀 있지만, 실제로는 훨씬 빨리 끝나는 경우가 많아([#41](https://github.com/wheresryan22/anatomy/issues/41)에는 10분 안에 끝났다는 보고가 있습니다) 아직 릴리스되지 않은 변경에서 Figure는 예상 시간을 알리지 않도록 바뀌었습니다([CHANGELOG](https://github.com/wheresryan22/anatomy/blob/main/CHANGELOG.md)). 모든 규모에서 첫 한 시간 안에 브라우저에서 열리는 동작 페이지를 만들고, 나머지 시간은 그 그림을 다듬는 데 씁니다.

카메라 기본값은 방위각 45도, 앙각 30도입니다. 저자는 엄밀히 말하면 이 각도가 아이소메트릭이 아니라 다이메트릭(dimetric) 투영이고, 진짜 아이소메트릭은 약 35.264도에서 내려다본다고 제작 과정 문서에서 부연하고 있습니다. 30도에서는 바닥의 모서리가 가로 2픽셀마다 세로 1픽셀씩 올라갑니다.

## Anatomy의 검증 도구

에이전트는 자기가 작성한 코드가 화면에 어떻게 그려지는지 직접 볼 수 없습니다. Anatomy는 이 한계를 메우기 위해 모든 검사가 그림, 숫자 한 줄, 종료 코드처럼 에이전트가 읽을 수 있는 결과로 끝나게 했습니다. 검사 도구는 세 가지입니다:

* **기하 감사**: [`kit/audit.mjs`](https://github.com/wheresryan22/anatomy/blob/main/kit/audit.mjs)는 부품마다 실제 3D 형상을 기록하고, 화면에서 겹치는 모든 쌍에 광선을 쏴 어느 쪽이 앞인지 측정해 그리는 순서를 정합니다. 파이프가 다른 물체를 관통하지 않는지, 모든 끝이 받침에 닿아 있는지도 함께 검사합니다.
* **선 끝 검사**: [`scripts/lines.mjs`](https://github.com/wheresryan22/anatomy/blob/main/scripts/lines.mjs)는 모든 선이 면, 다른 선, 점 위에서 끝나는지 브라우저에서 확인하고, 공중에서 끝나는 선이 하나라도 있으면 실패합니다.
* **스크린샷과 컨택트 시트**: [`scripts/capture.mjs`](https://github.com/wheresryan22/anatomy/blob/main/scripts/capture.mjs)와 [`scripts/drive.mjs`](https://github.com/wheresryan22/anatomy/blob/main/scripts/drive.mjs)는 헤드리스 Chrome으로 스크린샷, 확대 이미지, 느리게 재생한 프레임을 이어 붙인 한 장의 시트를 만들고, 스킬은 에이전트에게 만든 PNG를 모두 열어 보라고 지시합니다.

기하 감사는 Raptor 엔진 예제에서 시작됐습니다. 저자의 제작 과정 문서에 따르면 첫 버전은 원래 크기에서는 멀쩡해 보였지만, 4배로 확대하자 케이블이 주 덕트를 관통하고 노즐 음영이 계단처럼 끊겨 있었습니다. 처음 실행한 감사에서는 간섭(clearance) 문제 54건과 그리는 순서 문제 323건이 나왔고, 배포 상태에서는 두 수치 모두 0건입니다. 그리는 순서는 손으로 정한 값 대신 감사가 측정한 값을 쓰도록 바꿨습니다. 아래 그림은 같은 시점의 Raptor 엔진입니다. 왼쪽은 케이블이 덕트를 가로지르고 노즐 음영이 계단처럼 보이는 10월 4일 첫 라운드이고, 오른쪽은 케이블을 클램프로 묶은 10월 6일 배포 상태입니다:

![Anatomy Raptor 엔진 예제의 첫 라운드와 배포 상태 비교|1984x960](https://discuss.pytorch.kr/uploads/default/original/3X/7/8/78c7af4e77dfe3a4e4b2fc19a889c4c44dcbf8a3.jpeg)

저자는 큰 그림을 에이전트 하나에 맡기지 않고, 빌더와 서로 다른 관점의 리뷰어, 수정 담당으로 나눠 아무것도 발견되지 않을 때까지 라운드를 반복했습니다. 리뷰어는 빌더의 보고를 그대로 믿지 않고 페이지를 직접 빌드한 뒤 감사를 다시 실행하고 스크린샷을 찍었습니다. 터보팬 그림의 세 차례 리뷰에서는 스크린샷 309장이 남았습니다. 저자는 두 자동 검사의 한계도 *"The audit sees geometry and never the markup; the line check sees markup and never depth. Neither replaces looking."* 이라고 적어 두었습니다. 감사는 형상만, 선 검사는 마크업만 보므로 두 검사 모두 눈으로 확인하는 단계를 대신하지 못합니다.
