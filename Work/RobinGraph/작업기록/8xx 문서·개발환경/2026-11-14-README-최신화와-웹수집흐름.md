## 1. 작업 배경 및 문제 분석

기존 README에는 기능과 설치·환경·검증 안내가 있었지만 사용자가 채팅·탐색기·도감에서 무엇을 보고, 그 자료가 어떻게 준비되는지 한눈에 이어 읽기 어려웠다. 새소리는 운영 수집 실행기와 TEST 검토 화면·기록 저장·도감 재생이 서로 다른 단계다. 수집을 공개 승인으로 읽거나 저장된 검증 기록을 오늘의 서비스 실시간 상태로 오해하지 않도록 구분했다.

## 2. 해결 방안 및 설계

- 채팅·탐색기·도감 → API → 결과·출처·후속 조회·피드백 흐름을 첫 다이어그램으로 정리했다.
- 외부·검토 자료 → 로더 → 버전·출처·라이선스·종 연결 검증 → PostgreSQL/Neo4j → 웹 조회 흐름과 필요 시 사진·설명 캐시를 두 번째 다이어그램에 표시했다. 모든 자료가 매일 자동 갱신된다는 주장은 하지 않는다.
- Commons 후보 → 비공개 보관 → 인증된 검토 → 별도 사람 검토·공개 흐름은 세 번째 다이어그램으로 분리했다.
- 기존 구현·기록의 범위 설명이며 새로운 수집·자동 승인·공개를 실행하지 않는다. 단일 조건 추가 후속 질문과 semantic 일반화 미완료, 문헌 PPR 미구현을 유지했다.

문서만 변경하므로 앱 단위·회귀 suite, 실제 TEST·운영 DB/API와 브라우저 검증은 실행하지 않았다. root가 README와 앞선 백로그 정리 3파일의 로컬 Markdown 링크 83개를 검사해 누락 0, Mermaid 3개 fence 균형과 본문·흐름 검토, `git diff --check` 통과를 확인했다. 로컬 Mermaid renderer가 없어 실제 시각 렌더링은 미실행이다. GitHub 렌더 검증과 정적 구조 검사를 혼동하지 않는다. 이 기록의 링크는 최종 묶음 검사 대상이다.

## 5. 배포 및 형상 관리

- 대상: 저장소 문서와 Obsidian 작업기록. 앱 배포·재시작·이미지 교체·DB 변경 없음.
- 브랜치: `dev-codex`. 사용자가 변경 내용의 Git push를 명시 요청했다.
- root가 앞선 백로그 정리 문서 3개와 README 및 이 작업 기록을 검토해 commit/push한다. 이 본문 작성 시점에는 아직 실행 전이며 성공을 미리 기재하지 않는다.
- 실제 커밋 해시·원격 검증 결과는 root가 증거를 전달한 후 채팅·Obsidian 후속 절에 기록한다. 커밋할 문서에 자기 자신의 커밋 해시를 넣기 위한 추가 커밋은 만들지 않는다.
- push 전 root가 원격 `dev-codex`를 fetch하여 ahead 0·behind 0을 확인했다. 과거 비공개 이메일 보호 거부를 피하기 위해 기존 이력에서 확인한 GitHub noreply 이메일을 이번 새 commit 명령의 `-c user.email`에만 사용하며 영구 설정·기존 이력을 바꾸지 않는다. 이메일 값은 이 기록에 넣지 않는다.
- 앞선 Graphify·백로그 작업기록의 ‘당시 commit/push 미실행’ 이력은 보존한다.

## 6. 한계 및 후속 과제

문서 최신화와 Git push는 운영 배포가 아니다. RG-204·205·212의 사람 검토·일반화와 RG-409·507의 운영 승인·검토 한계를 그대로 유지한다. README에 설명된 배포·검증 결과는 해당 날짜의 저장 기록이며 이번 작업의 신규 성공으로 합산하지 않는다. docs-only 후속으로 Graphify AST를 반복 실행하거나 문서 semantic 재추출을 수행하지 않았다.
